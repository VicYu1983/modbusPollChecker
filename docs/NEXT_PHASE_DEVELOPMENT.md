# Modbus 案場回歸驗證工具：下一階段開發文件

## 1. 文件目的

本文件定義第一版完成後的下一階段開發方向。工具定位從「即時 Modbus TCP 檢查器」延伸為「案場 Modbus 線路健康度與回歸驗證工具」。

主要使用情境是在案場進行配線、網路、PLC、Gateway 或設備調整時，快速執行一輪檢查，並與調整前的基準結果比較，確認變更沒有造成其他設備異常。

本階段不以長時間監控平台為主要目標，也不優先加入雲端、多租戶或複雜告警功能。

## 2. 核心使用情境

### 2.1 調整前建立基準

1. 載入案場設定。
2. 執行全部啟用設備的檢查。
3. 確認結果符合預期。
4. 將本次檢查批次標記為基準批次。

### 2.2 案場調整後執行回歸測試

1. 進行線路、IP、交換器、PLC 或 Gateway 調整。
2. 重新執行全部設備檢查。
3. 系統將本次結果與基準批次比較。
4. 優先顯示新增失敗、逾時、回應變慢或回傳值改變的設備。
5. 使用者確認結果後，匯出測試報告。

### 2.3 單台設備快速診斷

當某台設備異常時，使用者可以重複檢查單台設備，觀察：

- 是否可以建立 TCP 連線。
- Modbus 回應是否逾時。
- Unit ID 與功能碼是否正確。
- 回應資料是否符合預期。
- 回應耗時是否明顯增加。

## 3. 本階段目標

### 必須完成

- 保存每次檢查的批次與結果。
- 支援基準批次。
- 支援兩個批次之間的差異比較。
- 顯示案場整體健康度與異常摘要。
- 顯示設備層級的回歸結果。
- 支援 CSV 與 HTML 報告匯出。
- 保留目前單台檢查、全部檢查與背景輪詢能力。

### 可以延後

- PDF 報告。
- Email、LINE、Teams 或 Webhook 通知。
- 使用者登入與權限。
- Modbus 寫入功能。
- Modbus RTU over TCP。
- 雲端集中管理。

## 4. 第一階段前置修正

在建立歷史與比較功能前，先修正目前檢查流程的語意與穩定性。

### 4.1 輪詢週期語意

自動檢查的預設週期為一秒；`scan_rate_ms=0` 代表沿用此預設值。行為定義如下：

- 新增設備預設 `scan_rate_ms=1000`。
- `scan_rate_ms=0`：自動檢查時使用預設一秒週期。
- `scan_rate_ms>0`：依指定週期執行背景檢查。
- 手動執行回歸測試時，不受設備輪詢週期影響。

### 4.2 結果與設定快照

每個檢查批次必須保存當時使用的案場設定快照，不能只保存設備名稱。否則日後修改 IP、Unit ID 或位址後，無法判斷舊結果是使用哪一份設定產生。

### 4.3 結果狀態一致性

前後端應共用下列狀態：

- `PASS`：通訊成功且資料符合預期。
- `FAIL`：通訊成功但資料不符合預期，或收到 Modbus Exception。
- `TIMEOUT`：連線或回應逾時。
- `CONFIG_ERROR`：設定驗證失敗。
- `UNKNOWN`：尚未檢查或沒有可用結果。

## 5. 功能設計

### 5.1 檢查批次

檢查批次代表一次完整的測試執行，至少包含：

- 批次識別碼。
- 案場名稱。
- 案場設定快照。
- 建立時間與完成時間。
- 執行模式：單台、全部或回歸測試。
- 執行結果：通過、失敗、逾時與設定錯誤數量。
- 操作者備註。

一次回歸測試應以批次為單位保存，不能只覆蓋各設備的最新狀態。

### 5.2 基準批次

每個案場最多先支援一個目前基準批次。

設定基準前必須符合：

- 批次已完成。
- 沒有 `FAIL`、`TIMEOUT` 或 `CONFIG_ERROR`，或使用者明確確認仍要建立基準。
- 基準批次的設定快照可被保留與讀取。

基準批次不是永久不可變資料。使用者可以在案場驗收或設備配置正式更新後，將新的合格批次設為基準。

### 5.3 回歸差異

每台設備的比較結果至少分為：

- `UNCHANGED_PASS`：前後皆通過，且關鍵回應沒有變化。
- `NEW_FAILURE`：基準通過，本次失敗或逾時。
- `RECOVERED`：基準失敗，本次通過。
- `VALUE_CHANGED`：通訊成功，但回傳值與基準不同。
- `LATENCY_DEGRADED`：仍然通過，但回應時間超過允許差異。
- `CONFIG_CHANGED`：本次設備設定與基準快照不同。
- `BASELINE_ONLY`：本次已不存在的設備。
- `NEW_DEVICE`：本次新增的設備，基準中沒有對應項目。
- `NO_BASELINE`：沒有可比較的基準批次。

比較依設備名稱進行。若未來允許設備改名，必須增加固定的設備識別碼，不能只依賴名稱。

### 5.4 回應時間比較

第一階段先使用簡單規則：

- 保存基準的 `elapsed_ms`。
- 允許設定固定增加值，例如 `+100 ms`。
- 允許設定比例，例如基準的 `2 倍`。
- 只有超過門檻且本次仍為 `PASS` 時，才標記為 `LATENCY_DEGRADED`。

不將一次偶發的慢回應直接視為線路故障。報告中應同時顯示基準值、本次值與比較門檻。

### 5.5 健康度摘要

案場摘要至少顯示：

- 啟用設備總數。
- 通過設備數。
- 失敗設備數。
- 逾時設備數。
- 設定錯誤數。
- 通過率。
- 平均回應時間。
- 最慢的設備。
- 新增異常數。

健康度百分比只作為摘要，不取代設備明細與差異結果。

## 6. 資料模型

建議將執行結果從目前的即時狀態中分離，增加以下概念模型。

### 6.1 CheckBatch

```json
{
    "id": "20260926-103000-001",
    "site_name": "案場 A",
    "schema_version": 1,
    "mode": "regression",
    "started_at": "2026-09-26T10:30:00+08:00",
    "completed_at": "2026-09-26T10:30:08+08:00",
    "device_count": 20,
    "pass_count": 18,
    "fail_count": 1,
    "timeout_count": 1,
    "config_error_count": 0,
    "note": "交換器更換後驗證",
    "baseline_batch_id": "20260926-090000-001"
}
```

### 6.2 CheckRecord

`CheckRecord` 沿用目前 `CheckResult` 的欄位，另外增加：

- `batch_id`
- `device_config_snapshot`
- `comparison_status`
- `baseline_record_id`
- `response_time_delta_ms`
- `response_time_ratio`

`values` 必須保存實際回傳值，但報告畫面可以依資料量限制顯示長度。

### 6.3 SiteBaseline

```json
{
    "site_name": "案場 A",
    "baseline_batch_id": "20260926-090000-001",
    "updated_at": "2026-09-26T09:10:00+08:00"
}
```

## 7. 儲存設計

### 7.1 儲存技術

建議使用 SQLite 作為本機歷史資料庫：

- 不需要另外安裝資料庫服務。
- 適合單機案場工具。
- 支援依時間、案場與設備查詢。
- 比單一 JSON 歷史檔更適合分頁與差異查詢。
- 日後仍可將設定 JSON 作為匯入匯出格式。

### 7.2 建議資料表

- `check_batches`
- `check_records`
- `site_baselines`
- `device_config_snapshots`

設定檔 JSON 與檢查歷史應分開保存。匯出案場設定時，不應把歷史結果混入設定檔。

### 7.3 保留策略

第一階段預設保留所有批次。日後可增加：

- 依日期刪除。
- 依批次刪除。
- 匯出後刪除。
- 限制資料庫容量。

刪除歷史資料前應要求使用者確認，且不能刪除目前基準批次，除非使用者先更換基準。

## 8. API 規格

| 方法 | 路徑 | 用途 |
|---|---|---|
| `POST` | `/api/check/batches` | 執行並建立檢查批次 |
| `GET` | `/api/check/batches` | 查詢批次清單 |
| `GET` | `/api/check/batches/{id}` | 取得批次摘要與結果 |
| `DELETE` | `/api/check/batches/{id}` | 刪除歷史批次 |
| `GET` | `/api/check/batches/{id}/report` | 匯出批次報告 |
| `GET` | `/api/check/batches/{id}/comparison` | 取得與基準的差異 |
| `POST` | `/api/sites/{site_name}/baseline` | 設定目前基準批次 |
| `GET` | `/api/sites/{site_name}/baseline` | 取得目前基準資訊 |
| `DELETE` | `/api/sites/{site_name}/baseline` | 清除基準 |

### 8.1 建立批次請求

```json
{
    "mode": "regression",
    "baseline_batch_id": "20260926-090000-001",
    "device_names": null,
    "note": "交換器更換後驗證"
}
```

`device_names` 為 `null` 時檢查全部啟用設備；指定清單時只執行選定設備，但局部檢查不應被誤標記為完整案場驗收。

### 8.2 批次執行狀態

若檢查設備數量增加，API 不應長時間阻塞 HTTP 請求。建議支援：

- 建立批次後立即回傳批次識別碼。
- 前端輪詢批次狀態，或日後改用 Server-Sent Events。
- 批次狀態包含 `PENDING`、`RUNNING`、`COMPLETED`、`FAILED`、`CANCELLED`。

第一階段仍可保留同步模式供少量設備使用，但 API 結構應預留非同步執行方式。

## 9. 前端畫面

### 9.1 快速回歸檢查

首頁應優先支援現場操作：

- 目前案場名稱。
- 基準批次時間。
- 「開始全部檢查」按鈕。
- 測試進度。
- 健康度摘要。
- 異常設備置頂。
- 一鍵查看差異與匯出報告。

### 9.2 批次歷史

顯示：

- 批次時間。
- 執行模式。
- 設備數量。
- 通過率。
- 新增異常數。
- 是否為目前基準。
- 備註。

### 9.3 設備差異明細

每筆設備顯示：

- 基準狀態與本次狀態。
- 基準回應時間與本次回應時間。
- 基準值與本次值。
- 設定差異。
- 錯誤訊息。
- 建議處理分類：檢查線路、檢查 IP、檢查 Unit ID、檢查資料位址或確認設備狀態。

### 9.4 設備設定畫面

沿用目前新增與編輯設備功能，但增加：

- 顯示該設備最近批次結果。
- 顯示目前是否存在基準。
- 顯示設定是否與基準快照不同。
- 可直接執行單台回歸檢查。

## 10. 報告格式

### 10.1 CSV

CSV 適合現場快速保存與交付，至少包含：

- 案場名稱。
- 批次時間。
- 基準批次時間。
- 設備名稱。
- IP、Port、Unit ID。
- 功能碼、位址與數量。
- 基準狀態。
- 本次狀態。
- 差異分類。
- 基準回應時間。
- 本次回應時間。
- 錯誤訊息。

### 10.2 HTML

HTML 報告適合直接用瀏覽器開啟與交付，包含：

- 案場摘要。
- 測試結論。
- 異常設備列表。
- 通過設備列表。
- 基準與本次結果比較。
- 測試設定快照摘要。
- 產生時間。

第一階段不要求前端完整重現報告頁面，後端可以產生獨立 HTML 檔案。

## 11. 後端分層調整

```text
API Layer
  | 批次建立、查詢、比較與報告下載
Batch Service
  | 建立批次、執行設備檢查、彙整結果
Comparison Service
  | 基準選擇、設定差異與結果差異判定
History Repository
  | SQLite 批次、結果與基準保存
Check Service
  | 既有並行檢查與背景輪詢
Modbus Adapter
  | pymodbus 連線與讀取
```

原則：

- Modbus Adapter 不知道批次與基準概念。
- Check Service 負責執行檢查，不負責產生報告。
- Comparison Service 不直接連線設備。
- Repository 不判斷 Modbus 狀態，只負責保存與查詢。
- API 層不直接操作 SQLite。

## 12. 測試策略

### 12.1 後端單元測試

必須覆蓋：

- 批次建立與完成狀態。
- 批次結果完整保存。
- 設定快照保存。
- 基準設定、替換與刪除。
- 新增失敗、恢復正常與新增設備判定。
- 回傳值改變判定。
- 回應時間門檻判定。
- 沒有基準時的結果。
- 部分設備檢查不被標記為完整驗收。
- 批次刪除與基準保護。

### 12.2 API 測試

- 建立批次後可查詢。
- 批次結果可依設備名稱與狀態篩選。
- 設定基準後可取得基準資訊。
- 差異 API 回傳穩定格式。
- 不存在的批次與設備回傳清楚錯誤。
- 報告下載的內容與批次一致。

### 12.3 前端測試

- 啟動全部檢查。
- 顯示執行中與完成狀態。
- 異常設備置頂。
- 基準設定確認。
- 差異分類顯示。
- 報告下載。
- 沒有基準時顯示正確狀態。

### 12.4 現場驗證

不在自動化測試中依賴真實設備。現場驗證至少使用：

- 一台正常設備。
- 一台關閉或拔線設備。
- 一個錯誤 Unit ID。
- 一個錯誤讀取位址。
- 一次刻意增加網路延遲的測試。

## 13. 開發階段

### Phase 2A：歷史基礎

- 修正輪詢週期語意。
- 建立 SQLite Repository。
- 建立批次與結果資料模型。
- 將單次與全部檢查保存為批次。
- 增加後端單元測試。

完成條件：重新啟動後仍可查詢之前的檢查批次。

### Phase 2B：基準與比較

- 建立基準批次 API。
- 實作設備狀態差異比較。
- 實作回傳值差異比較。
- 實作回應時間門檻。
- 增加差異明細畫面。

完成條件：調整一台設備造成失敗時，可以明確顯示為 `NEW_FAILURE`。

### Phase 2C：現場工作流程

- 建立快速回歸檢查畫面。
- 顯示進度與健康度摘要。
- 異常設備置頂。
- 支援備註與批次歷史。
- 支援 CSV 與 HTML 報告。

完成條件：使用者不需要進入多個設定頁面，就能完成一次案場回歸檢查並取得報告。

### Phase 2D：穩定性與部署

- 批次取消。
- 伺服器重啟後恢復查詢。
- 大量設備的查詢分頁。
- 資料庫備份與匯出。
- 前端 bundle 分割與啟動流程整理。

## 14. 非本階段目標

以下功能不列入本階段完成條件：

- 自動寫入線圈或暫存器。
- 自動修改 PLC 或設備設定。
- 取代 SCADA 或 EMS。
- 24 小時雲端監控服務。
- 複雜的機器學習異常預測。
- 依賴 Modbus Poll GUI 自動化。

## 15. 完成條件

本階段完成時，使用者應能：

- 為案場建立一個合格的基準批次。
- 在調整線路後一鍵執行完整檢查。
- 知道哪些設備是新增異常。
- 分辨通訊失敗、逾時、回應值改變與設定改變。
- 查看基準與本次回應時間差異。
- 查詢過去的檢查批次。
- 匯出可供現場紀錄或交付的回歸測試報告。

最終產品判斷標準不是「畫面有更多資訊」，而是：

> 使用者能否在案場完成一次線路調整，並快速證明調整前後的 Modbus 通訊健康度沒有退化。
